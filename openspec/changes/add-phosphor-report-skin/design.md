## Context

The usage report is generated by `.claude/skills/harness-usage-report/scripts/render.mjs`,
which fills `{{SLOT}}`s in `sources/base.html` and inlines `sources/fonts.css` +
`sources/style.css` + `sources/app.js` into one self-contained file. The daemon spawns
the skill as a black box (`server/usagereport.mjs:51`) and serves the newest output at
`/usagereport/report`; `web/src/features/usage/UsageReportView.jsx` embeds it in a
same-origin iframe.

`style.css` is 483 lines and unusually disciplined: outside its `:root` blocks the only
colour literals are four `#fff`. Everything else resolves through `var(--…)` or
`color-mix()`, so a skin is a token swap, not a selector rewrite. `app.js` is similarly
clean — 73 CSS-var references and exactly two colour-literal sites.

Commit `56d055e` added `:root[data-skin="phosphor"]` at `style.css:56-82` — 25 token
overrides plus three rules — activated by `UsageReportView.jsx:55-64` writing
`data-skin` onto the iframe's `contentDocument` after load.

The canonical Phosphor grammar lives in `docs/one-shot/phosphor-layout-02.html:34-300`
and `web/src/theme/skins/phosphor.roles.js`: black is the only surface; hierarchy is
border + glow + hue; colour is state (mint nominal, blue pending, amber caution, red
critical, greenMap idle) with **orange reserved for chrome**; `greenDim`/`amberDim` are
chrome-only, below AA for text; 2px/4px radii; a 3px orange frame with a 1px inset rule
and chamfered corners; dashed-amber focus; a CRT pass at `--z-crt:99`; discrete LED
meters instead of continuous fills.

## Goals / Non-Goals

**Goals:**
- A Phosphor rendition that reads as Phosphor, not as ZAPAC in Phosphor colours.
- Correct skin on the first painted frame, for both a host-embedded and a standalone report.
- Zero visual change to ZAPAC, structurally guaranteed rather than verified by eye.
- No colour literal left in shared chart code, guarded by a test.

**Non-Goals:**
- The bilingual English/Japanese layer (`.zt-jp`, `.jp`). That is app-shell chrome, and
  `e2e/phosphor.spec.mjs:281-284` enforces a never-orphan-a-bilingual-pair rule —
  introducing half of it into the report is scope creep against a live invariant.
- Restructuring the report's layout, sections, data or filters. Presentation only.
- Changing skin activation, persistence or isolation in the app shell. This change
  *consumes* the existing skin selection.
- Adding a skin switcher to the standalone report.
- Any new webfont. Phosphor's display face is a system condensed stack, so the report
  keeps its zero-network guarantee and `fetch-fonts.mjs` is untouched.

## Decisions

### Skin lives in its own stylesheet, appended last

`render_style()` (`render.mjs:186-190`) becomes `fonts.css + style.css + skin-phosphor.css`.
`style.css` returns to pure ZAPAC; every Phosphor rule moves to `sources/skin-phosphor.css`,
all scoped under `:root[data-skin="phosphor"]`.

Load order is load-bearing. `:root[data-skin="phosphor"]` and `:root[data-theme="dark"]`
have identical specificity (0,2,0), so the Phosphor file must come last to win — which
is also what makes Phosphor correctly dark-only regardless of the stored colour mode.

*Alternative considered:* keep one file. Rejected — the skin is about to grow from 25
lines to several hundred, and a single file makes "did this touch ZAPAC?" un-reviewable.
Separate files make ZAPAC's immutability visible in the diff.

### Skin arrives as a query parameter, resolved by the existing inline bootstrap

`base.html:5` already runs an inline script that seeds `data-theme` from `localStorage`
before the `<style>` block — which is why light/dark never flashes. Extend it to resolve
`?skin=` from `location.search`, then `localStorage['agents-report-skin']`, then nothing
→ ZAPAC. Apply the same precedence to `?theme=`. `UsageReportView.jsx:30`'s `reportSrc`
already builds a query string; append `&skin=` and `&theme=`.

The post-load `syncTheme` poke stays. The two paths are complementary, not redundant:
the query parameter fixes first paint, the DOM write handles a live *colour-mode*
change without reloading the iframe. Both write the same attribute, so they cannot
disagree.

**Corrected during implementation** (verified in the running app, task 7.5): the DOM
write does *not* carry a live **skin** switch, because `AppThemeProvider` renders
`<SkinProvider key={skin.id}>` — changing skin remounts the entire subtree, so
`UsageReportView` unmounts and the iframe is recreated. The user-visible requirement
still holds: the report is never *regenerated* (no skill spawn), and the fresh iframe
carries `&skin=` so it paints the new skin on its first frame with no ZAPAC flash.
But the iframe *is* reloaded on a skin change, and `syncTheme`'s skin branch only
ever runs against a freshly-loaded document. This is pre-existing app-shell
behaviour, not something this change introduced. Consequence for the design: the
query parameter is the load-bearing path for skin, and `syncTheme` is load-bearing
for colour mode. That is also why the iframe `src` must be captured once per mount
rather than tracked live — a `src` that followed `resolved` would navigate the
iframe on every light/dark toggle, discarding scroll position and legend state.

No daemon change — `/usagereport/report` serves a static file and ignores unknown query
parameters, and `?t=` already rides along.

*Alternatives considered:* `postMessage` — more ceremony, only works after load, and
the cross-origin capability it buys is unusable here (`UsageReportView.jsx:106-112`
documents why same-origin is load-bearing). Server-side injection of the attribute —
puts presentation state in the daemon and breaks the standalone file.

### Series colour is decoupled from status colour

Today `CFG.PALETTE` and `CFG.TOKEN` (`app.js:2-3`) reuse the *status* tokens
(`--ac`, `--azure`, `--amber`, `--sage`) as series colours. Under Phosphor that
collides: `--sage` would have to be simultaneously mint (status: nominal) and a
distinct fourth series hue. Introduce `--pal-1 … --pal-8` and `--tok-in/out/cr/cc`,
and have `app.js` read those.

ZAPAC's `--pal-*` values are exactly today's resolved colours, so this is a pure
indirection and ZAPAC renders identically — which is what makes the "ZAPAC output is
preserved" scenario checkable by diffing the regenerated example. Phosphor assigns
mint · blue · amber · greenMap · paper · teal · amberDim · greenDim, keeping orange
out of the data layer per the chrome-only rule.

Add `--paper-fg` — "legible on an accent-filled surface" — for the two treemap label
fills (`app.js:148`) and the four bare `#fff` in `style.css`. It is `#fff` under ZAPAC
and `var(--bg)` under Phosphor, mirroring `.stamp.fill > span` in the reference.

*Alternative considered:* branch on skin inside `app.js`. Rejected — it puts skin
knowledge in the data layer, and the whole file is otherwise skin-agnostic.

### The CRT pass moves to the top layer

`body::before` is `z-index:-1` (`style.css:89-95`); the current Phosphor skin overrides
only its `background`, so the scanlines sit *beneath* every card. The reference puts the
CRT pass at `--z-crt:99`, above content. Blank `body::before` to a flat surface fill and
move the scanline + vignette onto `body::after` — already `pointer-events:none` and used
for film grain, which Phosphor drops anyway — raised to `z-index:99`.

### Uppercase is opt-in, not opt-out

The reference sets `body{text-transform:uppercase}` and escapes `.prose,.msg,.path`.
Inverted here: uppercase is applied to the label and heading classes only
(`.shead-title h2`, `.card h3`, `.numlbl`, `.ratio-eyebrow`, `.tbl th`, `.fpill`, …).

This report is dense with model identifiers, file paths, project names and prose. A
blanket rule would mangle all of them and the opt-out list would be longer, and far
more fragile under future markup changes, than the opt-in list.

### Chamfer only where nothing overflows

`clip-path` clips descendants. `.card` hosts hover tooltips that deliberately overflow
(`.seg:hover::after` sits 17px above its bar, `style.css:193`) and scaled cells
(`.cal .c:hover`, `.heat .cell:hover`). Chamfering every card would shear them, so the
28px chamfer goes on `.flagcard` only, which has no overflowing children. Every other
panel gets the double frame — 1px orange border plus a `::before` inset hairline at
`inset:4px, opacity:.4` — which carries the signature without clipping. `.card` is
already `position:relative` and has no `::before`, so the pseudo-element is free.

### LED meters are achieved by masking, not by markup

`app.js` emits continuous fills as inline `style='width:…%'` (lines 190, 196, 201, 247,
454). Applying `mask-image:repeating-linear-gradient(…)` to `.bar-track`, `.sbar-track`,
`.ratio-meter` and `.sbars i` segments those fills into discrete LEDs in CSS alone. The
generator keeps emitting the same markup, so the entire meter treatment stays inside the
skin file and ZAPAC is untouched.

## Risks / Trade-offs

- **An unnoticed ZAPAC regression from the token indirection** → `--pal-*` are seeded
  with today's exact resolved values, and verification diffs a regenerated
  `example-report.html` against the pre-change render. A non-empty visual diff is a bug,
  not a judgement call.
- **`mask-image` support** → Shipping browsers all support unprefixed `mask-image`; the
  file already assumes modern engines (`color-mix`, `:has()`, standard `scrollbar-*` with
  a documented no-`::-webkit-scrollbar` decision at `style.css:84-86`). If a mask fails,
  the meter degrades to the existing continuous fill — legible, just not segmented.
- **Query parameter and live-sync disagreeing** → Both write the same `data-skin`
  attribute from the same `skinId`; there is no second source of truth to drift from.
- **Phosphor's report accent differs from the app's** → Deliberate. The app reserves
  orange for chrome and the report needs a primary *data* hue, so `--ac` maps to mint.
  Documented in the skin file so it does not read as an error.
- **Skin file drifting from the vendored theme** → The report cannot import
  `phosphor-console-theme` (it must stay a self-contained file), so its palette is a
  transcription. Values are sourced from `phosphor.roles.js` and the reference layout
  with the AA-corrected red `#F04438`, not raw `redHi #E2280F` — the correction
  `e2e/phosphor.spec.mjs:296-309` exists to enforce.

## Migration Plan

No data migration, no schema change, no daemon change. The report is regenerated on
demand and each generation is a fresh file, so there is nothing to migrate forward.

Rollback is reverting the commit: `style.css` reabsorbs its Phosphor block,
`skin-phosphor.css` disappears, and `app.js` returns to literal colours. Reports already
on disk are self-contained and keep rendering with whatever skin they were built against.
