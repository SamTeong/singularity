# Rust PTY compatibility

The Rust PTY bridge for the registry integration step is `server/rust-pty-backend.mjs`. `spawn()` resolves after the Rust service accepts the operating-system spawn and returns a handle with `id`, `generation`, `onData(callback)`, `onExit(callback)`, `activate()`, `write(text)`, `resize(cols, rows)`, and `kill()`. Register both callbacks before `activate()`; events received earlier are buffered. Output callbacks receive UTF-8 strings, and exit is delivered after the decoder tail. `write`, `resize`, and `kill` return promises. `stop()` kills and reaps owned PTY children before stopping the service, with a bounded process-kill fallback.

## Windows ConPTY selection

The previous `node-pty` configuration used `useConptyDll: true`, which selects its package-relative `conpty/conpty.dll`. `portable-pty` 0.9.0 has no equivalent selector: it checks for the system ConPTY exports, tries to load a bare-name `conpty.dll`, and falls back to `kernel32.dll` when that attempt fails. The bare name follows Windows loader search and existing-module behavior; it does not guarantee that the DLL beside the executable is selected. This migration therefore does not promise node-pty DLL-selection parity.

Version-specific sources: [portable-pty 0.9.0 Windows loader](https://docs.rs/crate/portable-pty/0.9.0/source/src/win/psuedocon.rs), [node-pty ConPTY selection](https://github.com/microsoft/node-pty/blob/main/src/win/conpty.cc), [portable-pty API](https://docs.rs/portable-pty/0.9.0/portable_pty/).

## Windows process termination

`portable-pty` 0.9.0's Windows `WinChildKiller::kill()` reverses the Win32 `TerminateProcess` BOOL result: it reports nonzero (success) as an error and zero (failure) as success. The service therefore duplicates the live child's owned process handle before transferring the child to its waiter, then calls `TerminateProcess` directly and checks its documented result. If the process is already exited, `GetExitCodeProcess` confirms that state and kill completes successfully; if termination fails, the service rechecks process state on that same handle and otherwise reports the Win32 error. The original child remains owned by the waiter, which still performs wait/reap and drains reader output before exit.

Sources: [portable-pty 0.9.0 Windows child killer](https://docs.rs/crate/portable-pty/0.9.0/source/src/win/mod.rs), [Microsoft TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), [Rust BorrowedHandle](https://doc.rust-lang.org/stable/std/os/windows/io/struct.BorrowedHandle.html).

## Windows ConPTY startup cursor query

Microsoft's [`CreatePseudoConsole` contract](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole) says that with `PSEUDOCONSOLE_INHERIT_CURSOR`, the host should asynchronously handle the cursor-state request received on the pseudoconsole output and reply on its input; leaving the request unanswered can block pseudoconsole initialization. `portable-pty` 0.9.0 enables this flag. The Rust service therefore handles only an exact leading `ESC[6n` on Windows, replies once with `ESC[1;1R`, and suppresses that initialization query from application output. It preserves a fragmented query until it can match or reject it, and forwards later DSR queries and every leading mismatch unchanged. This startup policy is Windows-only; non-Windows PTY output and input are unchanged.

Windows runtime evidence on the implementation host: the real bridge tests exercise command spawn, arguments, cwd/env, input/output, resize, explicit kill, exit, shutdown reap, and unaided startup. Rust filter unit tests cover later application DSR forwarding and fragmented or mismatched startup prefixes. Windows ConPTY may itself answer application DSR in cooked mode, so the byte-preservation guarantee is tested at the service reader boundary. Both normal and 1 MiB queued-write cases passed after the owned-handle fix. During a live helper probe, PowerShell inspected the exact `singularity-backend.exe --pty` PID and observed `KERNEL32.DLL` among loaded modules; no `conpty.dll` appeared in that process module list. This is an observation for that host and run, not a universal selection claim. A POSIX run or cross-target compilation does not establish Windows behavior. No macOS runtime parity is claimed.
